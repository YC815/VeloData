| **W1-2**  | **任務設定資料探索**  | 申請 Strava API Key 學習 OAuth 驗證 了解 TTS、功率區間                                           | ★★★★☆           | **完成**：完成 API 申請與 OAuth 2.0 授權流程（含 `refresh_token` 換取 `access_token`），並釐清 TSS 公式與 IF／功率區間概念。 **省思**：初期把 `average_watts` 當 TSS 計算依據，後來才理解應使用 `weighted_average_watts`（NP）。 **改進**：探索階段就應先讀完 API 回傳 schema，並整理成 `docs/strava_api_gotchas.md` 這類文件，減少後續除錯時間。                                                                                                                                                                                                                                                                                                                                        |
| **W3**    | **資料抓取**          | 撰寫 Script 撈取近一個月的騎乘 JSON 資料 提取出 average_watts, heartrate, moving_time 等關鍵欄位 | ★★★★☆           | **完成**：透過 `GET /athlete/activities` 抓取活動（後續擴展為近 90 天），在 `enrich_activity()` 提取功率、心率、時間、爬升等欄位，並加入 DB 快取避免重複打 API。 **省思**：計畫寫獨立 Script，實作上直接整合進 Flask，功能達成但不利於離線分析或批次匯出。 **改進**：補一支 `scripts/fetch_activities.py` 將 JSON 落地存檔；對無功率計活動（`device_watts: false`）應更早規劃 fallback（如 `suffer_score`）。                                                                                                                                                                                                                                                                            |
| **W4**    | **演算法實作**        | 實作 TSS 計算公式 將每趟室內間歇訓練（如 SST 課表）轉化為具體的訓練點數                          | ★★★★☆           | **完成**：依公式實作 `calc_tss()`，並依 IF 對應甜區／閾值／VO2max 等訓練語意；進一步實作 PMC（CTL／ATL／TSB）曲線。 **省思**：間歇課的 NP 能反映強度，但無功率計的室內騎行 TSS 仍會缺值。 **改進**：建立以心率或 RPE 估算 TSS 的第二路徑；用已知 SST 課表（如 2×20 min @ 88–93% FTP）做 golden test 驗算。                                                                                                                                                                                                                                                                                                                                                                               |
| **W5**    | **期中審核/介面原型** | 完成初版簡易 Web Dashboard。顯示本週總訓練量                                                     | ★★★★★           | **完成**：Flask + Tailwind 儀表板已上線，本週 TSS／距離／騎乘時間三卡合一；並超出原型範圍，加入 PMC 圖表、訓練狀態（TSB）、賽事倒數、武嶺預測等模組，並部署至 Zeabur。 **省思**：期中目標已達成且功能偏多，但複雜度提高後，新使用者 onboarding 成本變高。 **改進**：Dashboard 應維持「一屏看懂本週負荷」的核心，進階功能收進 Analysis／Racing 分頁；補 README 與 `.env.example` 說明，方便他人複現。                                                                                                                                                                                                                                                                                     |
| **W6**    | **疲勞預警**          | 加入「心率/功率比」分析功能 若同樣瓦數下心率偏高，程式自動輸出「疲勞警告」                       | ★★★☆☆           | **完成**：以 PMC 為基礎實作 `calc_tsb_status()`，依 TSB（CTL−ATL）自動輸出四級疲勞警示（>5 狀態良好可高強度／>0 輕微疲勞建議 Z2／>−10 中度疲勞注意恢復／≤−10 過度訓練強制休息），並以語意色（green→yellow→orange→red）呈現於儀表板。 **省思**：原計畫的「同瓦數下心率漂移（EF／心率功率比脫鉤）」並未照規格做出；目前 `avg_hr` 雖有抓取與顯示，但疲勞判斷實際走的是訓練負荷（TSB）路徑，而非單次騎乘的心率/功率解耦。兩者衡量的疲勞層次不同：TSB 是長期累積，心率漂移是當下狀態。 **改進**：補做單次活動的 decoupling 分析——取前半/後半段 NP 與平均心率算 EF 衰退率，>5% 觸發「當日疲勞」警告，與 TSB 的長期警示互補；需改抓 activity streams（逐秒功率/心率），summary 欄位不足以計算。 |
| **W7**    | **實測與優化**        | 進行一次 20 分鐘 FTP 測驗 將真實數據匯入系統，校正程式中的功率區間設定                           | ★★★★☆           | **完成**：建立 `ftp_calibration.py` 多維度 FTP 估算引擎——MMP 近似模型（掃近期 15–40 min 最高 NP，套用時長換算係數 20min×0.95／30min×0.97）＋物理逆推模型（指定活動＋路段反推 FTP），兩者加權（有物理逆推：MMP 60% + Physics 40%；無：100% MMP），估算結果即時回饋 TSS 與武嶺預測。 **省思**：尚未進行原計畫的「正式 20 分鐘場地 FTP 測驗並匯入校正」，目前 FTP 來自既有騎乘的 MMP 反推，仍帶系統性低估（沒人會在一般訓練中全力 20 分鐘）。 **改進**：實際執行一次標準 20 min FTP test（暖身後全力 20 分 × 0.95），把真值與 MMP 估算對照，校正換算係數；並用已知 SST 課表（2×20 min @ 88–93% FTP）做 golden test 反算驗證引擎準確度。                                                     |
| **W8**    | **分享省思**          | 整理開發紀錄與訓練曲線圖 評估程式數據如何輔助自己維持訓練動力。                                  | ★★★★☆           | **完成**：整理完整開發紀錄（`docs/strava_api_gotchas.md` 踩坑文件、`CLAUDE.md` 架構說明），PMC 訓練曲線（CTL／ATL／TSB 90 天）與武嶺破三預測上線並部署至 Zeabur 公開存取，形成可複現的個人化監控儀表板。 **省思**：數據確實改變了訓練決策——TSB 轉紅時會主動安排恢復，避免以往「感覺還行就硬騎」導致的隱性過勞；客觀數字比身體感覺更早一步示警。把抽象的「疲勞」量化成 TSB 數字後，維持訓練的動力從「靠意志力」變成「看趨勢線」。 **改進**：目前仍偏個人工具，缺長期追蹤的成效驗證（FTP 是否真的隨 CTL 提升）；下一階段應累積整季數據，回頭分析「CTL 成長率 vs FTP 進步」的相關性，驗證本計畫對「西進武嶺破三」的實質幫助。                                                               |
