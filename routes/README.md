# routes/ — 路線資料庫指南

本目錄存放所有指標路段的定義檔案。每條路線是一份獨立的 JSON，
演算法核心（`predictor.py`）讀取這些檔案來進行模擬，不綁定任何特定路線。

---

## 新增路線 SOP

1. 在此目錄建立 `<route_id>.json`（例如 `fenggueizui.json`）
2. 依照下方 Schema 填入資料
3. 無需修改 `predictor.py` 或 `app.py`，`list_routes()` 會自動發現新檔案

---

## JSON Schema

```jsonc
{
  "id":             "route_id",          // 與檔名相同，英文小寫+底線
  "name":           "路線顯示名稱",       // 顯示在 UI 的中文名
  "description":    "起點→終點",          // 簡短描述
  "distance_km":    52.56,               // 總距離（公里）
  "elevation_m":    2593,                // 總爬升（公尺）

  "physics": {
    "Crr":  0.004,   // 滾動阻力係數（公路：0.003-0.005）
    "CdA":  0.35,    // 風阻面積（m²）（標準騎行姿勢：0.32-0.40）
    "rho":  1.15,    // 空氣密度（kg/m³）（高海拔可降至 0.90-1.10）
    "loss": 0.03     // 傳動損耗（3% = 典型公路車）
  },

  "sub_x_targets": [
    {"label": "破 X 小時", "minutes": 240}
    // 列出使用者關心的突破目標，會顯示在 Benchmark Lab Sub-X 區塊
  ],

  "segments": [
    {
      "name":      "起點-終點",   // 路段名稱（用於顯示與除錯）
      "dist":      16.29,        // 路段距離（公里）
      "grade":     0.018,        // 平均坡度（小數，例如 3% = 0.030）
      "alt_decay": 1.00          // 海拔功率衰減係數（見下方說明）
    }
  ]
}
```

---

## 欄位詳解

### `alt_decay`（海拔功率衰減係數）

高海拔氧氣稀薄，人體有氧功率會下降。此係數乘上有效 FTP 後得到該路段的實際輸出功率：

```
P_seg = FTP_eff × alt_decay
```

| 海拔高度 | 建議 alt_decay |
|---------|--------------|
| < 500 m  | 1.00         |
| 500–1000 m | 0.97–0.99  |
| 1000–2000 m | 0.90–0.96 |
| 2000–3000 m | 0.77–0.89 |
| > 3000 m | < 0.77       |

武嶺（3275 m）最後一段設為 `0.77`，地理中心碑（約 500 m）設為 `1.00`。
**同一路線中，越後面的路段 alt_decay 應越低。**

### `grade`（坡度）

使用小數而非百分比：

| 標示 | grade 值 |
|-----|---------|
| 平路 | 0.000–0.010 |
| 緩坡 | 0.010–0.050 |
| 中坡 | 0.050–0.080 |
| 陡坡 | 0.080–0.120 |
| 極陡 | > 0.120    |

### `physics.rho`（空氣密度）

若路線大部分在高海拔，建議整體調低 rho：
- 台北盆地（海拔 10 m）：`1.22`
- 北宜公路（平均 600 m）：`1.18`
- 武嶺（平均海拔 2000+ m）：`1.15`
- 大禹嶺以上：`1.10`

## 演算法流程（供參考）

```
FTP × (1 + TSB × 0.002)   →   FTP_eff（考慮疲勞的有效功率）
FTP_eff × alt_decay        →   P_seg（各路段實際功率）
binary search              →   v（速度，使 P_wheel ≈ P_seg）
dist / v                   →   t_seg（路段耗時）
Σ t_seg                    →   total_time（完賽時間）
```

反向求解（Sub-X）：對 FTP 做 binary search，找到使 `total_time ≤ target` 的最低 FTP。
